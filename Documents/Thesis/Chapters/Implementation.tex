\section{Asset Administration Shell Server}
\label{sec:aas_server}

The implementation uses the Eclipse BaSyx \ac{AAS} server, which provides MongoDB-based persistence, MQTT event notification on data changes, REST API endpoints compliant with the \ac{AAS} specification, and a web-based monitoring interface. The server is deployed as a Docker container for consistent environments.

\subsection{Operation Invocation Delegation}
\label{subsec:invocation_delegation}

A key implementation pattern is the \texttt{invocationDelegation} qualifier, which enables \ac{AAS} Operations to delegate execution to external services. When an Operation is invoked via the \ac{AAS} REST API, the BaSyx server forwards the request to an external HTTP endpoint specified in the qualifier.

This pattern connects the standardized \ac{AAS} interface to the physical asset simulators (or real PLCs in production). The invoker services are implemented as FastAPI applications that:
\begin{enumerate}
    \item Receive the operation request with input parameters
    \item Execute the corresponding machine operation
    \item Return results in \ac{AAS}-compliant format
\end{enumerate}

The detailed configuration for Docker networking and invoker implementation is provided in Appendix~\ref{app:invocation_delegation}.

\section{Agent Communication Infrastructure}
\label{sec:xmpp_config}

The implementation uses Prosody as the \ac{XMPP} server for agent communication. Prosody was selected over alternatives (e.g., ejabberd) due to better compatibility with the SPADE Python framework and straightforward PubSub configuration.

The server provides:
\begin{itemize}
    \item Point-to-point messaging between agents
    \item Publish-subscribe functionality for event distribution
    \item SSL/TLS encryption for secure communication
\end{itemize}

Agents are registered as \ac{XMPP} users and configured with administrator privileges to enable PubSub node creation. The detailed server configuration is provided in Appendix~\ref{app:xmpp_config}.

\section{Agent Implementation Challenges}
\label{sec:agent_challenges}

Several technical challenges were encountered during agent implementation. This section documents the issues and their solutions, as they provide insights for future implementations.

\subsection{BDI vs. Finite State Machine}

During initial development, an attempt was made to implement agent behavior using a Finite State Machine (FSM) pattern. This approach proved problematic for \ac{BDI} agents:

\begin{itemize}
    \item \textbf{Rigidity}: FSMs enforce fixed state transitions, preventing dynamic plan selection based on beliefs and goals.
    \item \textbf{Loss of Reactivity}: \ac{BDI} agents should react to belief changes opportunistically; FSMs constrain behavior to explicit transitions.
    \item \textbf{Commitment Conflict}: FSMs require commitment to a predefined structure, contradicting the \ac{BDI} principle of deliberation over intentions.
\end{itemize}

The final implementation uses AgentSpeak plans triggered by belief changes, allowing context-dependent plan selection rather than predetermined paths.

\subsection{SPADE Belief Storage Limitation}

A limitation was discovered in the SPADE \ac{BDI} implementation: storing list-like strings as belief values causes incorrect parsing due to internal string splitting. For example, a belief containing \texttt{"[08:00-08:30, 08:30-09:00]"} is truncated at the first bracket.

\textbf{Workaround}: Complex data structures are stored in \ac{AAS} submodels rather than directly in beliefs. The agent retrieves structured data through the ResourceAASClient when needed, ensuring data integrity.

\subsection{PubSub Subscriber Crosstalk}

The SPADE PubSub implementation uses a single global callback for all subscriptions. Multiple calls to \texttt{set\_on\_item\_published()} overwrite previous handlers, causing messages from different topics to be delivered to incorrect handlers.

\textbf{Solution}: A single callback is registered that dispatches messages based on the topic node identifier. This pattern ensures each topic's messages reach the appropriate handler without interference. The implementation is shown in Appendix~\ref{app:pubsub_dispatch}.

\section{Summary}

This chapter presented the implementation of the Type 3 \ac{AAS} prototype, highlighting:
\begin{itemize}
    \item The hybrid deployment architecture combining Docker containers with host-based agents
    \item The \texttt{invocationDelegation} pattern for connecting \ac{AAS} Operations to external execution
    \item Technical challenges in \ac{BDI} agent implementation and their solutions
\end{itemize}

The implementation demonstrates that integrating \ac{BDI} agents with \ac{AAS} infrastructure is feasible using existing open-source tools, though framework-specific workarounds are required. Detailed configuration files and code listings are provided in Appendix~\ref{app:implementation_details} for reproducibility.
