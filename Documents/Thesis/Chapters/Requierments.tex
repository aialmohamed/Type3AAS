\chapter{Use Cases and System Requirements}
\label{ch:requirements}

The preceding chapter established the theoretical foundations and identified the research gaps that this thesis addresses. Based on these findings, this chapter derives concrete use cases and system requirements for implementing a \ac{Type3AAS} using \ac{BDI}-based \ac{MAS}. Following the systems engineering approach, the use cases are derived from the research questions identified in Section~\ref{subsec:critical_analysis}, and the system requirements are subsequently derived from these use cases. Detailed specifications are provided in Appendix~\ref{app:requirements}.

\section{From Research Questions to Use Cases}
\label{sec:rq_to_uc}

The critical analysis in Chapter~\ref{ch:literature} identified three main contributions that this thesis aims to provide: bidirectional \ac{AAS} integration enabling agents to both read from submodels and invoke Operations, foundational submodels supporting proactive behavior, and a proof-of-concept validation with production resources.

To demonstrate and validate these contributions, a production scenario involving drill machines (in virtual environment) was selected. The \textit{SmartDrillSystem} serves as the proof-of-concept implementation, consisting of multiple \ac{AAS}-represented drill machines (ResourceAAS) that can be orchestrated by production orders (ProductionAAS). This scenario allows the demonstration of all key \ac{Type3AAS} capabilities: autonomous behavior, peer-to-peer communication, negotiation, and proactive decision-making.

\section{System Components}
\label{sec:system_components}

The SmartDrillSystem comprises four main components that work together to realize \ac{Type3AAS} functionality:

\textbf{ResourceAAS} represents the digital twin of each drill machine, combining the standardized \ac{AAS} structure with a \ac{BDI} agent runtime. Each ResourceAAS maintains submodels describing the asset's operational state, capabilities, and interaction parameters, while the embedded agent provides autonomous decision-making and negotiation capabilities.

\textbf{ProductionAAS} manages production orders and coordinates the allocation of tasks to available resources. When a drilling order is received, the ProductionAAS agent queries the registry for available resources, initiates negotiations based on defined criteria (such as time availability), and delegates the production plan to the selected ResourceAAS.

\textbf{AAS Registry} provides a central discovery service where all \ac{AAS} components register themselves upon initialization. This enables dynamic discovery of available resources without hardcoded dependencies between components.

\textbf{Event Broker} implements an MQTT-based messaging infrastructure that enables asynchronous, event-driven communication between components. This supports real-time status updates and reactive behavior across the distributed system.

\section{Use Cases}
\label{sec:usecases}

The SmartDrillSystem is specified through three primary use cases that cover the complete lifecycle of the system: Startup, Drilling Order, and Shutdown. Additionally, two included use cases (AAS Registration and Drill Operation) are invoked by the primary use cases to handle specific sub-processes. \subsection{UC1: System Startup}

The System Startup use case describes the initialization sequence when an operator starts the SmartDrillSystem. During startup, the system initializes all components including the Event Broker, AAS Registry, ResourceAAS instances, and ProductionAAS. The startup process includes the \textit{AAS Registration} (UC2) sub-process, where each ResourceAAS registers itself with the central registry, making it discoverable for subsequent production orders. Upon successful initialization, the system transitions to the ready state and awaits drilling orders. If any component fails to initialize, the system displays appropriate error messages and attempts retry procedures.

\subsection{UC3: Drilling Order}

The Drilling Order use case represents the core production scenario and demonstrates the key \ac{Type3AAS} capabilities. When an operator submits a drilling order with specified parameters (depth, diameter, material type), the system delegates this order to the ProductionAAS. The ProductionAAS agent then retrieves available resources from the registry and initiates a negotiation process with all registered ResourceAAS agents. Using time availability as the primary negotiation criterion, the ProductionAAS selects the most suitable resource and assigns the production plan. 

The selected ResourceAAS then executes the \textit{Drill Operation} (UC4) sub-process, which handles the actual drilling execution through the bidirectional \ac{AAS} integration. During this sub-process, the ResourceAAS agent updates its beliefs from submodels, forms intentions, and invokes standardized \ac{AAS} Operations on the physical asset. Throughout execution, the ResourceAAS publishes status events, and upon completion, the system returns to the ready state for the next order. Alternative flows handle invalid input parameters and drilling failures with appropriate error handling and recovery procedures.

\subsection{UC5: System Shutdown}

The System Shutdown use case ensures graceful termination of the SmartDrillSystem. When an operator initiates shutdown, the system stops all active production processes, completes or cancels pending drilling orders, deregisters all ResourceAAS from the registry, and terminates all components in the proper sequence. This controlled shutdown procedure prevents data loss and ensures system integrity.

\subsection{Included Use Cases}

In addition to the primary use cases described above, two included use cases support the main workflows:

\textbf{UC2: AAS Registration} is included in UC1 (System Startup) and handles the dynamic registration of ResourceAAS instances with the central registry. Each ResourceAAS sends its identification information, capabilities, and communication endpoints to the registry, enabling participation in subsequent negotiation processes.

\textbf{UC4: Drill Operation} is included in UC3 (Drilling Order) and describes the execution of drilling operations by a ResourceAAS. This use case demonstrates the bidirectional integration between the \ac{BDI} agent and the \ac{AAS}, where beliefs are derived from submodels and intentions are executed through standardized Operations.

\section{System Requirements}
\label{sec:requirements}

Based on the use cases defined above, this section summarizes the system requirements organized into functional and non-functional categories. The complete requirements specification with detailed descriptions is provided in Appendix~\ref{app:requirements}.

\subsection{Functional Requirements}

The functional requirements are organized into four groups addressing different aspects of the system.

\subsubsection{System Specifications (REQ\_1 -- REQ\_8)}

The system-level requirements define the overall architecture and fundamental capabilities of the SmartDrillSystem. These requirements specify that the system must comprise ResourceAAS, ProductionAAS, an Event Broker, and an AAS Registry as its core components. The system must provide standardized communication between \ac{AAS} instances and support event-based messaging through the broker. Furthermore, the requirements mandate that \ac{AAS} components operate autonomously, possess decision-making capabilities, and collaborate through interdependent processes. These requirements directly address the \ac{Type3AAS} characteristics of autonomy, intelligence, and collaboration identified in Chapter~\ref{ch:literature}.

\subsubsection{ResourceAAS Specifications (REQ\_10 -- REQ\_20)}

The ResourceAAS requirements specify the structure and behavior of drill machine representations. Each ResourceAAS must contain an agent interface supporting FIPA \ac{ACL} communication, a \ac{BDI} agent runtime, standardized submodels, and an asset interface for physical device communication. The required submodels include an Operational State Submodel (tracking current state and performance KPIs), a Knowledge Submodel (capturing resource constraints and environmental conditions), a Capability Submodel (describing available skills and service parameters), and an Interaction and Scheduling Submodel (defining communication endpoints and collaboration protocols). Additionally, the ResourceAAS must support event publishing and subscription, and participate in negotiations with ProductionAAS using time availability as the decision criterion.

\subsubsection{ProductionAAS Specifications (REQ\_21 -- REQ\_31)}

The ProductionAAS requirements define the structure for production order management. Similar to ResourceAAS, each ProductionAAS must contain an agent interface, agent runtime, and specialized submodels. The required submodels include an Identification Submodel (containing order metadata), a Process Plan Submodel (defining tasks, precedences, and required capabilities), a Services Catalog Submodel (listing available machine skills), an Interface and Endpoints Submodel (specifying communication methods), and an Execution State and Tracking Submodel (monitoring current progress and status). The ProductionAAS must coordinate with ResourceAAS through FIPA \ac{ACL} negotiation protocols.

\subsubsection{MAS/BDI Specifications (REQ\_32 -- REQ\_34)}

The \ac{MAS}/\ac{BDI} requirements specify the integration between agent concepts and the \ac{AAS} structure. Each ResourceAAS must maintain defined belief sets derived from its submodels, representing the agent's knowledge about itself and its environment. Agent desires (objectives) must be defined for each resource, representing the goals that drive agent behavior. Finally, agent intentions (plans) must be specified, defining the procedures the agent executes to achieve its objectives. These requirements ensure that the \ac{BDI} architecture is systematically integrated with the \ac{AAS} meta-model.

\subsection{Non-Functional Requirements (NFR\_1 -- NFR\_5)}

Beyond functional capabilities, the system must satisfy quality requirements essential for industrial deployment. The interoperability requirement mandates compliance with IDTA \ac{AAS} specifications to ensure compatibility with the broader Industry 4.0 ecosystem. Scalability requirements ensure that new ResourceAAS can be added without modifying existing components. Reliability requirements specify graceful handling of component failures with appropriate error messages. Maintainability requirements call for modular architecture supporting future extensions. Finally, performance requirements specify that agent negotiations must complete within acceptable time bounds for the proof-of-concept demonstration.
\subsection{Considerations for Production Deployment}
\label{subsec:production_considerations}

The requirements defined above focus on demonstrating the feasibility of \ac{Type3AAS} in a proof-of-concept context. A production-ready system deployed in an industrial environment would need to address additional requirements that are beyond the scope of this thesis but are acknowledged here for completeness.

\textbf{Availability and Fault Tolerance.} Production systems require high availability, often specified as 99.9\% uptime or higher. This necessitates redundant components, failover mechanisms, and the ability to recover from partial system failures without losing production data or state. The current prototype does not implement redundancy or automatic recovery.

\textbf{Information Security.} Industrial systems must protect against unauthorized access, data manipulation, and cyber attacks. This includes authentication and authorization for all \ac{AAS} access, encrypted communication channels (TLS/SSL), audit logging of all operations, and compliance with standards such as IEC 62443 (Industrial Cybersecurity). The prototype uses unencrypted communication and does not implement access control.

\textbf{Performance and Scalability.} While NFR\_5 specifies negotiation completion within 5 seconds for the proof-of-concept, production systems may require sub-second response times for real-time control scenarios. Additionally, the system must scale to hundreds or thousands of resources while maintaining performance. Load testing and performance optimization are not addressed in this work.

\textbf{Integration with Enterprise Systems.} Production deployments typically require integration with Manufacturing Execution Systems (MES), Enterprise Resource Planning (ERP), and other business systems. This includes standardized interfaces, data format transformations, and transaction management.

\textbf{Regulatory Compliance.} Depending on the industry, additional requirements may arise from regulations such as FDA 21 CFR Part 11 (pharmaceutical), ISO 13485 (medical devices), or automotive quality standards (IATF 16949).

These considerations are discussed further in the outlook (Chapter~\ref{ch:outlook}), where future work directions are identified for transitioning the proof-of-concept toward production readiness.

\section{Summary}
\label{sec:req_summary}

This chapter has derived use cases and system requirements for implementing a \ac{Type3AAS} using \ac{BDI}-based \ac{MAS}. Three primary use cases were defined (Startup, Drilling Order, and Shutdown), supported by two included use cases (AAS Registration and Drill Operation) that handle specific sub-processes. From these use cases, 26 functional requirements and 5 non-functional requirements were derived, organized into System Specifications, ResourceAAS Specifications, ProductionAAS Specifications, and MAS/BDI Specifications.

The requirements directly address the research gaps identified in Chapter~\ref{ch:literature}. Bidirectional \ac{AAS} integration is addressed through requirements for agent-asset communication and the mapping of \ac{BDI} components to \ac{AAS} elements. Foundational submodels are specified through detailed submodel requirements for both ResourceAAS and ProductionAAS. The proof-of-concept is enabled through the complete system specification covering all operational scenarios. The following chapter presents the conceptual design that realizes these requirements.
